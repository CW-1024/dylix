# Build198：旧会话的普通AI长回复补充整理

版本1.0.8 / Build198，FLEX配套仍为1.0.0 / Build196。继承Build197余额自动识别，没有改模型协议、工具审批、人设正文、项目文件或用量计费逻辑。

## 用户截图意味着什么

整理前891.3KiB，整理后283.4KiB，仍超过应用固定256KiB文本JSON保护预算，所以Runtime在调用模型传输器之前停止。这不是服务商的context-window错误，不代表模型只有256KiB窗口，也不表示已经消耗145115 tokens。该数字由文本JSON字节粗估，服务商实际输入量显示“未报告”；本次没有发出模型请求。

FLEX查询95次 /469.4KiB、文件读取22次 /67KiB等是**整理前的原始记录**，不代表这些数据仍全部发送，也不是计费token数。原诊断没有给出整理后按角色和schema的构成，无法单靠截图确定283.4KiB的具体来源。

## 确认并补齐的代码缺口

旧实现卸载大工具参数 /结果、折叠完整历史工具批次，但没有卸载普通的历史assistant长回复。完整会话持续保留这些生成的报告 /代码；即使新问题很短，旧会话仍可被固定预算拦住。

新实现只在已有工具整理后仍超预算、且本轮确实提供`read_context`时，从最旧的普通assistant长回复开始转换为明确标记的不完整预览，保留摘要性前缀、原文bytes / SHA256及`message:N`引用。优先保留最近普通回复；仍超预算且最近回复本身很大时，它也可使用同样可回读预览。原始会话从不被发送副本覆盖。

引用在删除折叠的工具结果行**之前**按原始ordinal生成，避免工具折叠后引用错位。回读仍受当前会话 /唯一引用 / Unicode分页校验约束。带原生provider_items的普通消息保持完整，不独立改写签名reasoning或原生continuation。未完成调用、最近工具观察、用户原话、系统 /人设及工具schema仍保留既有策略，不静默丢弃。

本次没有简单扩大256KiB保护预算，也没有将字节限制冒充已知模型token窗口。若保留部分确实不可整理，仍会拦截，提示查看剩余构成。此限制也仍可能对很长的用户输入、系统提示或native provider continuation生效；这类内容需要用户明确精简或在后续引入有明确定义的模型预算设置。

## 诊断改进

上下文用量新增：

- `assistantMessagesOffloaded`：普通历史AI回复卸载次数。
- `afterCompositionBytes`：整理后系统 /人设、用户消息、AI回复 /工具参数 /历史回执、工具结果、schema和JSON结构占用。各项总和等于整理后统计字节；图片仅保留数量，不冒充图片token估算。
- `blockedBeforeRequest`：是否在本机拦截。被拦截时明确显示“未向模型发送”“本次无模型请求用量”，不会把旧usage当本次消耗。

原始工具排行继续保留，明确标注“整理前，非本次发送量”。旧保存诊断缺少新字段仍可查看。新的上下文事件仍清空上一轮的usage，服务商随后返回真实值才显示实际输入tokens。
