# Dylix 1.0.7 build189：补丁失败诊断与恢复反馈

日期：2026-11-05

## 用户现象与证据边界

截图中的红色卡片是 `propose_patch` 准备代码修改失败，并非编译错误。失败的提案不会写入项目；后续提案成功、经审批应用、再构建成功，与这些历史失败记录可以同时存在。

旧实现把零处匹配和多处匹配合并为同一个错误，没有告诉模型匹配数量及位置。截图没有完整工具入参，因此不能确认每次失败究竟是重复方法、旧文本、空白差异，还是其他精确匹配差异。“补丁没有实际变化”表示该批修改最终没有净变化，不等于用户目标已经完成。

## 本次修改

- 区分 `patch_before_not_found`、`patch_ambiguous`、`patch_no_change`。
- 返回文件路径、匹配数量、候选行号、磁盘原文 SHA-256 和建议读取范围。
- 区分磁盘行号与尚未应用的批内修改缓冲区行号。
- CRLF/LF 差异仅作为诊断提示，不自动归一化或覆盖文件。
- 修正重叠匹配的唯一性判断：`aaa` 在 `aaaa` 中不再被视为唯一匹配。
- Runtime 将结构化恢复信息送入下一轮模型工具结果，并保留在工具事件中。
- 指引模型重读最新原文、加入唯一类上下文、避免复制 UI 折行及行号；失败时不生成可应用提案。

工具 schema、默认 developer prompt、路径和敏感内容检查、审批流程保持原有设计。没有引入模糊替换或默认替换第一处。没有增加强制重试次数限制，不能保证模型永远不会再次提交错误补丁。旧会话中的失败历史不会被改写。
